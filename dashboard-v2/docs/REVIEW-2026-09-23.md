## Écarts à traiter

### Priorité haute

1. **Activer les configurations déjà disponibles.** Les boards Merchant `kit`,
   `consumables` et `gifts` sont activés mais ne contiennent aucune règle. Seul
   Eadroma possède un loadout explicite, et uniquement le style AOE. Le code est
   prêt, mais le comportement des autres personnages repose encore sur les
   valeurs des scripts.
2. **Ajouter des tests de parcours UI.** La logique pure et le builder sont bien
   couverts, mais les hooks React, la reconnexion WebSocket et les parcours
   sauvegarde → conflit → déploiement n'ont pas de test navigateur automatisé.
3. **Préparer le dépôt public.** Le dossier n'est pas encore un dépôt Git. La CI
   est prête, mais il faut choisir une licence, décider quels assets Adventure
   Land peuvent être redistribués, initialiser Git et définir le remote.

### Priorité moyenne

1. **Réduire les modules centraux.** `server/builder.ts`, `shared/schema.ts` et
   `MerchantPage.tsx` concentrent encore trop de responsabilités. Les séparer par
   domaine rendra les prochaines règles moins risquées.
2. **Typer le backend historique.** Plusieurs frontières utilisent encore `any`,
   surtout l'analyse AST, le stockage SQLite et les réponses de déploiement.
3. **Mettre les fixtures du builder dans le dashboard.** La suite complète dépend
   toujours du dossier `../code`, alors que la CI ne lance que la suite autonome.

## Features proposées

### P1 — Conformité live des loadouts

Afficher, pour chaque style, le loadout désiré face à l'équipement réellement
porté : pièce absente, mauvais niveau, slot incorrect et raison du blocage. Un
bouton peut ouvrir directement l'éditeur concerné. Cette vue rend les loadouts
vérifiables sans lire les logs.

### P1 — Centre d'alertes opérationnelles

Produire des alertes actionnables pour potion sous le seuil, inventaire presque
plein, healer absent, stand fermé alors qu'il est activé, télémétrie périmée et
drift de build. La santé de flotte existe déjà côté serveur ; il reste surtout à
l'exposer et à ajouter les seuils métier.

### P2 — Planificateur Merchant

Afficher une file d'actions : livraisons, ventes NPC, échanges, upgrades, achats
Ponty et stand. Chaque ligne indique `prêt`, `bloqué` ou `terminé`, avec la raison
exacte : or réservé, item équipé, niveau cible, quantité manquante ou personnage
indisponible. Le stand doit afficher la configuration désirée face aux slots live.

### P2 — Historique et rollback de profils

Conserver les dernières révisions avec auteur local, date et diff lisible, puis
permettre export, import et restauration. Le contrôle de révision actuel fournit
déjà une bonne base pour cette fonction.

### P2 — Recherche globale d'items

Étendre la banque en un localisateur couvrant banque, inventaires, équipements et
stand. Une recherche doit répondre « où est cet item, à quel niveau et en quelle
quantité ? » et signaler si une règle Merchant ou un loadout le réserve.

### P3 — Budgets d'upgrade et compound

Ajouter les exclusions permanentes, les niveaux cibles de compound, le type de
scroll, le budget maximum par cycle et une simulation avant exécution. Cette
fonction doit partager le moteur de réservation avec les loadouts et le stand.

### P3 — Release GitHub reproductible

Ajouter des tests Playwright sur les parcours critiques, une vérification des
fixtures du builder en CI, une version sémantique, un changelog et des releases
automatiques. Le workflow actuel fournit déjà lint, build et tests unitaires.

## Ordre recommandé

1. Remplir les règles de loadout et de consommables utilisées en production.
2. Construire la conformité live et le centre d'alertes.
3. Ajouter le planificateur Merchant.
4. Découper le builder et le schéma pendant l'ajout des budgets compound/upgrade.
5. Ajouter les parcours UI automatisés, choisir la licence et initialiser GitHub.
